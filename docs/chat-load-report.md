# 聊天压力测试记录

测试日期：2026-10-08（Asia/Shanghai）。以下先记录修复前数据；发送路径修复后的对照见文末。修复前单个阻塞客户端会拖慢无关会话；修复后本地相同测试中的无关会话 P95 恢复到 4ms。

## 环境与方法

- Java 17.0.12，32 个可见逻辑处理器，测试 JVM 最大堆约 3894 MB。
- 独立 Spring Boot 测试实例和独立内存 H2 数据库（PostgreSQL 模式），随机 HTTP 端口；不连接运行中的业务数据库。
- 登录 Token 校验、HTTP 接口、会话权限、事务保存及 WebSocket 推送使用实际实现；账号存在性查询使用 mock。
- 客户端与服务器在同一 JVM、本机回环网络。每条正文约 200 字符，客户端持续读取推送。
- 各阶段以固定数量工作线程发起请求，收到响应后继续下一条，属于闭环负载；HTTP 延迟从请求开始计算，不包含线程池任务排队时间。
- 每个阶段校验数据库新增消息数量，并按接收者身份和 clientId 去重统计推送。下表的连接数包括管理员连接。
- 前三个私聊阶段各先发送 20 条预热消息。随后 3 万条阶段复用已预热连接，因此其速率不能直接与冷启动阶段比较。

## 最后一轮实测

P95 表示 95% 的请求在该时间内得到 HTTP 响应。速率是本阶段平均值，不能作为生产容量承诺。

| 场景 | WebSocket 连接 | 并发请求 | 消息数 | 耗时 | 请求/秒 | HTTP P95 | 推送 P95 | 入库 | 收到/预期推送 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 买家私聊 | 11 | 10 | 200 | 0.38s | 528.45 | 35ms | 34ms | 200 | 400/400 |
| 50 买家私聊 | 51 | 25 | 500 | 0.59s | 848.03 | 57ms | 56ms | 500 | 1000/1000 |
| 100 买家私聊 | 101 | 50 | 1000 | 0.93s | 1072.10 | 89ms | 89ms | 1000 | 2000/2000 |
| 100 买家，3 万条消息 | 101 | 50 | 30000 | 10.36s | 2895.19 | 44ms | 44ms | 30000 | 60000/60000 |
| 50 成员群发 | 50 | 20 | 300 | 0.24s | 1263.87 | 28ms | 27ms | 300 | 15000/15000 |

以上阶段共 32000 条计量消息，全部入库；78400 次预期推送全部观察到，HTTP 错误为 0。预热消息及以下慢连接对照不计入这两个汇总数字。

## 慢连接对照

建立两个独立私聊，交替向它们发送 50 条消息，10 路并发。先测无连接的 HTTP/数据库基线，再给第一条会话加入一个模拟发送阻塞 250ms 的 WebSocketSession；第二条会话没有该慢连接。

| 场景 | HTTP P95 | 速率 | 第一条会话 P95 | 无关第二条会话 P95 |
| --- | ---: | ---: | ---: | ---: |
| 基线 | 4ms | 3921.97 请求/秒 | 3ms | 4ms |
| 第一条会话有 250ms 阻塞连接 | 2095ms | 7.67 请求/秒 | 2093ms | 2095ms |

两组均 50 条消息全部入库且没有 HTTP 错误。慢连接阶段不统计真实网络推送：它通过 mock 阻塞 `sendMessage`，用于证明同步发送路径的影响，不等同于真实弱网测试。

原因：`ChatService.send` 是全局 `synchronized`，提交数据库后仍在该方法内同步调用 `publishRoom`，后者直接向各连接发送。单连接写入阻塞会占住整个发送锁，其他会话的请求也排队。`ConcurrentWebSocketSessionDecorator` 能处理并发发送与缓冲限制，但不能据此保证当前全局发送锁不被阻塞。

优先修复方向：让持久化和连接推送的阻塞相互隔离，使用有界队列并明确慢连接的关闭策略；修改后用同一慢连接对照回归，验证无关会话延迟恢复。此次只测试和记录，没有修改业务实现。

## 修复后的回归

已修改共享 WebSocket 处理器：入库后的推送只入队，32 个发送工作线程执行网络写入。每个连接最多 128 条待发送消息（含正在发送的消息）、64KB 正文缓冲；同一连接最多一个活动发送任务，按入队顺序发送，每发一条重新调度，避免热点连接持续占用工作线程。队列满或调度拒绝时关闭连接，已保存消息由重连历史补齐。

发送超过 5 秒时触发关闭，巡检每秒执行一次；内置 Tomcat 的阻塞写超时也设为 5 秒。关闭动作在独立有界执行器中运行，避免再次阻塞 HTTP 保存路径。底层超时属性依据 [Tomcat WebSocket 文档](https://tomcat.apache.org/tomcat-10.1-doc/web-socket-howto.html)。数据库提交锁仍保留，保障当前单实例消息提交顺序；本次未修改数据结构或鉴权。

| 同一慢连接对照 | 整体 HTTP P95 | 无关会话 HTTP P95 |
| --- | ---: | ---: |
| 修复前基线 | 4ms | 4ms |
| 修复前：250ms 阻塞连接 | 2095ms | 2095ms |
| 修复后基线 | 5ms | 5ms |
| 修复后：同一个 250ms 阻塞连接 | 5ms | 4ms |

修复后再次运行全部压测场景：正常负载的 32000 条消息全部入库，78400 次预期推送全部收到，HTTP 错误为 0。100 买家、30000 条消息阶段用时 9.81 秒，HTTP P95 为 38ms，推送 P95 为 37ms；50 成员群发的 HTTP P95 与推送 P95 均为 20ms。

新增单元测试覆盖：阻塞连接不影响健康连接、单连接消息顺序、消息数限额、字节限额、超时关闭及清空积压。原有 13 个后端测试与新增 3 个测试均通过；压测入口及其继承的集成用例也通过。

本次慢连接阶段仍只测 HTTP/持久化延迟，未计量该模拟慢连接的最终送达时间；它的积压在测试结束时清理。正常网络推送完整性在前述独立场景中计量。异步推送不是送达确认，客户端仍需靠历史补取恢复。

修复前原始快照保留在 `docs/chat-load-results.json`；修复后快照为 `docs/chat-load-results-after.json`。大量连接同时阻塞仍可能占满发送工作线程，但队列有界且真实 Tomcat 写入有超时；本轮未验证这种极端场景，不将结果解释为任意慢连接数量下都无延迟。

## 复现

PowerShell 在仓库根目录执行：

```powershell
.tools/apache-maven-3.9.9/bin/mvn.cmd -f backend/pom.xml test '-Dtest=ChatLoadTest' '-Dchat.load=true' -q
```

测试入口：`backend/src/test/java/com/clothsell/module/mall/websocket/ChatLoadTest.java`。必须显式开启 `chat.load`，普通测试不执行压测。原始结果输出至 `backend/target/chat-load-results.json`，本轮快照保存为 `docs/chat-load-results.json`。
